# Project Notes

- Current architecture source of truth: `openspec/changes/adopt-effect-4-backend-architecture/`. The completed Cloudflare blueprint is historical context.
- Backend target: Effect 4 throughout services, Layers, tagged errors, Schema, HTTP/`HttpApi`, Effect SQL PostgreSQL, workflows, configuration, resource safety, concurrency, and telemetry. Drizzle ORM 1.0 RC supplies the Effect-native PostgreSQL schema/query/migration layer.
- Permanent backend removals: Hono, oRPC, Zod, and Kysely. Frontend-only choices are independent.
- Runtime: Cloudflare first with deterministic test Layers for portability; PostgreSQL first through a Cloudflare platform connection expected to use Hyperdrive; Durable Objects first for actors; Rivet deferred.
- Storefront SDK: one Effect API contract with browser HTTP and server-only Cloudflare Service Binding transports.
- Auth exception: Better Auth stays temporarily behind an Effect adapter; do not reimplement auth. Review direct wrapping, `effectify`, and future official support later.
- Migration: pre-production clean break with no backfill or legacy API compatibility; verified vertical slices start with `store` and delete their legacy implementations.
- Current reviewed application cohort: Effect `4.0.0-beta.93`, exact-pinned in the root catalog. Reconfirm the catalog, resolved lockfile cohort, and architecture canaries on every upgrade.
- Effect HTTP task 4.2 baseline: `@ecommerce/api` now owns shared pagination, request identity, success-envelope, paginated-success, and sanitized serialized-error Effect Schemas in `packages/api/src/http-api-schemas.ts`; auth-specific identity/session contracts remain deferred to task 5.1.
- Effect HTTP task 4.3 baseline: `packages/api/src/effect-http-middleware.ts` owns request-scoped context/auth/permission/deadline/telemetry wrappers plus `HttpApiMiddleware.Service` contracts; Better Auth implementation remains deferred behind `EffectHttpAuthService` for task 5.
- Effect HTTP task 4.4 baseline: `packages/api/src/effect-http-api-assembly.ts` deterministically assembles admin/storefront `HttpApi` group contributions, records route fingerprints, and rejects duplicate method/path pairs or group identifiers before Worker/OpenAPI/SDK generation.
- Effect HTTP task 4.5 baseline: `apps/server/src/effect-http-worker.ts` is the native Alchemy v2 Effect Worker entrypoint, while `effect-http-worker-runtime.ts` composes canonical admin/storefront APIs, group handler Layers, isolate runtime Layers, and Worker HTTP support. The legacy Hono entrypoint remains deployed until migrated module groups are ready.
- Effect HTTP task 4.6 baseline: `packages/api/src/effect-http-openapi.ts` derives deterministic admin/storefront OpenAPI snapshots from canonical Effect `HttpApi` assemblies via `OpenApi.fromApi`; snapshots live in `packages/api/src/__tests__/__snapshots__/effect-http-openapi.test.ts.snap` and are generated contract artifacts, not hand-authored API definitions.
- Effect HTTP task 4.7 baseline: `@ecommerce/storefront-sdk` owns the public fetch-based storefront SDK transport. Prefer `@ecommerce/storefront-sdk/http`, `createStorefrontHttpClientForApi`, and `createStorefrontHttpClient` for browser and fullstack server runtimes with WHATWG `fetch`; `@ecommerce/storefront-sdk/browser` remains a browser-safe compatibility alias. The transport uses Effect `FetchHttpClient.layer` over public `fetch` and has no Cloudflare binding/server runtime exports.
- Effect HTTP task 4.8 baseline: `@ecommerce/storefront-sdk/cloudflare` owns the server-only Cloudflare Service Binding storefront SDK transport. `createStorefrontServiceBindingClientForApi` and `createStorefrontServiceBindingClient` adapt a structural binding `fetch` into Effect `FetchHttpClient.layer`, default to `https://storefront.service-binding` for URL construction, preserve generated `HttpApiClient` types, and are intentionally not re-exported from the package root.
- Effect HTTP task 4.9 baseline: `packages/storefront-sdk/src/__tests__/transport-conformance-suite.ts` is the shared SDK transport parity harness. It runs public HTTP and Cloudflare Service Binding factories against one storefront `HttpApi` contract and asserts identical decoded result shape, generated client method usage, HTTP method, and relative route, with only the transport origin differing.
- Effect HTTP task 4.10 baseline: browser bundle boundaries now live in `apps/web/src/__tests__/no-effect-imports.test.ts` and `packages/storefront-sdk/src/__tests__/browser-bundle-boundary.test.ts`. Browser code bans static, side-effect, and dynamic imports of `@ecommerce/storefront-sdk/cloudflare`; SDK root/http/browser entries must not re-export the Cloudflare transport or import server runtime bindings.
- Auth task 5.1 baseline: `packages/auth/src/auth-contracts.ts` is the Effect-native auth contract surface. It owns branded user/session/permission IDs, `AuthRole`, structured permissions, `AuthIdentity`, `AuthSession`, and schema-backed tagged errors for unauthenticated, expired-session, permission-denied, and adapter-failure cases. Better Auth inferred types remain a private adapter concern.
- Auth task 5.2 baseline: `packages/auth/src/effect-auth-service.ts` defines the provider-independent `EffectAuthService`, `CurrentAuthRequestContext`, request-context Layer helpers, and anonymous/authenticated context constructors. Root exports use `EffectAuthServiceTag`/`EffectAuthServiceShape` while the legacy Better Auth factory still owns the temporary `AuthService` type name.
- Auth task 5.3 baseline: `packages/auth/src/better-auth-effect-adapter.ts` privately wraps Better Auth-compatible `api.getSession({ headers })` behind `EffectAuthService`. It exposes `betterAuthEffectAuthLayer` and `makeBetterAuthEffectAuthService` by file path only, translates anonymous/success/rejected provider results into Effect auth contexts or tagged failures, and keeps concrete Better Auth types off the public package root. `packages/auth/src/auth-adapter-utils.ts` owns reusable provider-boundary helpers for future auth adapters.
- Auth task 5.4 baseline: Better Auth request/result/failure translation is explicit and private. The adapter clones inbound `Headers`, decodes unknown provider sessions through `AuthSession`, maps malformed results to `AuthAdapterFailure(reason: "invalid-response")`, maps rejected provider calls to `AuthAdapterFailure(reason: "provider-rejected")`, and preserves expired sessions as `AuthSessionExpired`.
- Auth task 5.5 baseline: Effect HTTP protected groups now authenticate through `EffectAuthServiceTag` and the private Better Auth adapter at Worker runtime assembly. `packages/api/src/effect-http-middleware.ts` installs provider-neutral auth context and permission guards; `apps/server/src/effect-http-worker-runtime.ts` wires the adapter when `auth` is provided and otherwise fails closed for protected routes. The adapter subpath is exported from `@ecommerce/auth/better-auth-effect-adapter` for composition only, not from the public package root.
- Auth task 5.6 baseline: Better Auth persistence is a temporary provider-private seam during Kysely removal. `packages/auth/src/factory.ts`, the generated D1 auth migration, and `bun run --cwd packages/auth auth:gen` remain in place for Better Auth-owned tables only; commerce modules must depend on `EffectAuthServiceTag` and auth contract IDs instead of Better Auth storage/types. Do not migrate Better Auth tables into commerce Effect SQL/Drizzle tasks until the auth-provider research change selects the replacement/retention path.
- Auth task 5.7 baseline: Cloudflare Worker auth boundary coverage now asserts protected API groups read session cookies through the Better Auth Effect adapter, reject missing/expired sessions with 401, reject missing permissions with 403, and sanitize rejected provider failures without leaking Better Auth/provider internals.
- Auth task 5.8 baseline: Follow-up OpenSpec change `evaluate-effect-auth-provider-options` tracks the long-term auth-provider decision. It compares direct Better Auth wrapping, `@effectify/node-better-auth`, and future official support, with hard gates for Cloudflare Worker compatibility, provider-neutral `EffectAuthServiceTag` semantics, sanitized failures, session-cookie behavior, and explicit auth persistence ownership.
- Store/marketplace boundary clarification: Better Auth organizations are identity workspaces and must remain provider-private behind the Effect auth boundary. Commerce stores are domain settings/defaults records, not tenants or auth organizations. Future merchant/vendor/market/marketplace support should arrive through commerce modules or plugins with explicit links to stores/products/orders/workflows and provider-neutral organization IDs where needed.
- Store task 6.1 baseline: `packages/modules/store/src/__tests__/store-service-regression.test.ts` locks framework-independent service behavior before the Effect rewrite: lazy singleton default creation, defaults projection, currency normalization/deduplication, trimmed locale/name/timezone updates, changed-field event publication, no event for timestamp-only no-op updates, and rejection when the default currency is outside supported currencies. Store package test script now runs both historical `_tests` and new `__tests__`.
- Store task 6.2 baseline: store domain/API schemas and inferred types now come from Effect Schema in `packages/modules/store/src/domain/store.schema.ts` and `store.types.ts`. Branded `StoreIdSchema` is domain-only; serialized API records use plain `StoreSerializedIdSchema`. Legacy Zod schemas are isolated in `packages/modules/store/src/contracts/legacy-zod-contract-schemas.ts` only to keep the oRPC bridge alive until task 6.7 deletes it.
- Store task 6.3 baseline: generic store `Error` throws are replaced by schema-backed tagged errors in `packages/modules/store/src/domain/store.errors.ts`: `StoreInvalidIdentifier`, `StoreCurrencyListEmpty`, and `StoreDefaultCurrencyUnsupported`. The current Promise-based store service throws these expected errors temporarily until task 6.4 moves the service into typed Effect error channels.
- Store task 6.4 baseline: `createStoreService` now returns Effect-native operations with typed `StoreServiceFailure`, `StoreService` and temporary `StoreRepositoryService` compose through Layers, and legacy oRPC/server/checkout seams use the explicit `createStorePromiseService` facade until their later migration tasks remove Promise adapters.
- Store task 6.5 baseline: `StoreRepository` is now the Effect-native repository contract with `StoreRepositoryService`; D1 remains isolated as `StoreLegacyRepository` until the PostgreSQL/Drizzle task replaces it. The in-memory store repository is `Ref`-backed, exports `createInMemoryStoreRepositoryLayer`, and is covered by the shared repository contract harness.
